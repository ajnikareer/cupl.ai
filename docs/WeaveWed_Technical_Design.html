Technical Design Document

How the WeaveWed voice and chat AI companion is built: architecture, tech stack, AI models, the QLOO integration, memory and learning, data model, APIs, security, deployment and the build plan. This is the reference for developers and AI coding agents working on the product.

1. System Overview

WeaveWed is an agent-first application. The AI agent is the main interface: users talk to it by voice or chat, and it creates Event Spaces, collects tastes, calls QLOO, builds plans and keeps learning. The screens (dashboard, plan view, to-dos, profile) are views of the same data the agent works on.

Clients

One responsive React + Vite PWA for web and mobile. It can be wrapped with Capacitor for app stores later.

Agent backend

A FastAPI service that runs the agent loop, voice proxy, tools, memory and plan engine.

Intelligence

Gemini for reasoning, voice and extraction. QLOO for taste intelligence. Embeddings for episodic memory.

Data

Firestore for all app data, plus Firestore vector search for memories. Cloud Storage for media.

2. Design Principles

  • Live only. No seeded or mock data in the product. If an upstream call fails, the user sees a real, friendly error. Demo data lives in a separate environment, built later.
  • Agent first, UI second. Everything the UI can do, the agent can do through tools.
  • Event Space gate. Planning tools are only exposed to the model when an active Event Space exists. Otherwise the agent runs in Guide mode.
  • Grounded recommendations. Every plan item that comes from taste data carries its QLOO entity ID and the signals behind it, which is what the "Why this?" card shows.
  • Human in control. Destructive or major changes (budget, venue swap, deleting a space) require a confirmation card.
  • Privacy by design. Per-partner visibility on tastes, plus Surprise Mode isolation.
  • Keys stay on the server. The client never holds Gemini or QLOO credentials.
  • Model names are config, not code. Gemini model versions change often, so every model ID is an environment variable.

6. Voice Pipeline

Client side

  • getUserMedia → AudioWorklet that downsamples to 16 kHz, 16-bit PCM, mono, little-endian, in 20–40 ms frames.
  • Frames go out as binary WebSocket messages to /ws/voice?space={id}, authenticated with a Firebase ID token in the first message.
  • Playback: incoming 24 kHz PCM chunks go into an AudioWorklet ring buffer. On an interrupted event the buffer is flushed immediately (barge-in).
  • Live transcripts of both sides render as chat bubbles, so voice and text share one history.
  • Widget events (taste pickers and so on) render while the agent is speaking.

Server side (Voice Proxy)

  • Opens a Gemini Live session per client connection with: system instruction (persona + mode + memory context), tool declarations, voice config, input and output transcription turned on, and automatic voice activity detection.
  • Relays audio both ways and intercepts toolCall messages. It runs the tool in the Tool Layer, sends the toolResponse, and forwards any UI widget to the client.
  • Slow tools (QLOO + plan building) run non-blocking where the model supports it, so the agent can keep talking ("Let me find what you'd both love…").
  • Saves both transcripts to conversations/{id}/turns and enqueues learning when the session ends or every N turns.
  • Session limits: Live sessions have a maximum duration. The proxy uses context-window compression / session resumption where available, and otherwise reconnects transparently with a rolling summary.

Persona and voice

  • A prebuilt warm female voice (configurable via LIVE_VOICE_NAME), language en-IN, Hinglish understood.
  • Style rules in the system prompt: short sentences, a natural warm tone with light humour, use the user's name, one question at a time, confirm before decisions, never read out long lists (show a widget instead).

7. Agent Orchestrator

Modes

ModeWhenTools exposed
GuideUser has no active Event Spaceapp_help, create_space, list_spaces, render_ui
SetupA space exists but required fields are missingGuide tools + update_space, invite_partner
PlannerThe space is ready (required fields complete)All tools
CompanionThe user asks about their partner, gifts or surprisesAll tools + partner_insight, surprise_* (privacy-filtered)

The mode is computed on the server for each turn from Firestore state. It is never inferred by the model, so the Event Space gate can't be bypassed by the prompt.

Per-turn context assembly

system_prompt =
  PERSONA                         # warm planner style rules
+ MODE_INSTRUCTIONS[mode]         # what's allowed now
+ USER_CARD        (name, partner name, love status)
+ ACTIVE_SPACE     (type, city, dates, budget, missing_fields[])
+ PROFILE_FACTS    top 25 facts for this user (by confidence × recency)
+ COUPLE_DNA       shared loves, differences, vibe (privacy-filtered)
+ EPISODES         top 3 KNN past experiences relevant to space + last message
+ DECISIONS        confirmed decisions in this space
+ CONVERSATION     rolling summary + last 20 turns

The loop

  1. Build the context → call the model with the tools allowed in this mode.
  2. If there are tool calls: validate the args (Pydantic) → check permissions (couple membership, space ownership, privacy) → execute → return the result to the model. At most 6 tool hops per turn.
  3. Stream text tokens and widget events to the client.
  4. Persist the turn, the tool calls and the token usage.
  5. Enqueue a learning task (de-duplicated per conversation, every 4 turns or at the end of a session).

Guardrails

  • Plan items must reference a candidate returned by a tool (QLOO entity or user-provided). The model can't invent a venue or restaurant as a "recommendation".
  • Prices are always labelled as estimates.
  • Off-topic requests are answered briefly, then the agent steers back to planning.
  • Safety settings stay at their defaults; no medical, legal or financial advice beyond budgeting.

12. Learning Loop

  1. Trigger: a Cloud Task learn(conversation_id, from_turn), or a feedback event (like/skip/done) or episode save.
  2. Extract with GEMINI_EXTRACT_MODEL and a JSON schema: 
    ExtractionResult = {
  facts:     [{category, text, sentiment, confidence, about: "self|partner"}],
  decisions: [{space_id, summary}],
  feedback:  [{item_id, signal}],
  life_events:[{type, date}]     // e.g. engagement date mentioned
}
  3. Resolve: facts without an entity → QLOO search → attach the entity ID if the top match is confident.
  4. Reconcile against existing facts (same entity, or embedding similarity > 0.9):
    • Same direction → mentions++, confidence = min(1, c + 0.1)
    • Opposite sentiment → the newer fact wins, the old one is marked superseded_by
    • "about: partner" facts are stored as hints on the partner profile at low confidence (0.4) and shown to the partner for confirmation
  5. Feedback weights: liked = +0.15 to the item's source signals, skipped = −0.1, done/booked = +0.25.
  6. Recompute the Couple DNA if any fact changed.
  7. Re-plan: plan sections that depend on changed categories → status stale → revise_plan for those sections only → write a new plan version → FCM push "Updated your Sangeet playlist".
  8. Post-event check-in: the scheduler finds spaces with end date < today → the agent asks how it went → the answer becomes an episode (summary, rating, highlights, lowlights, embedding) and its facts are extracted.

Couple blending algorithm

A = insights(signals = Priya's shared+private facts)        # her list with affinity
B = insights(signals = Karan's facts)
C = insights(signals = both)                                 # joint list
score(e) = 0.5·C.affinity(e) + 0.25·A.affinity(e) + 0.25·B.affinity(e)
         + 0.15 if e in A∩B  ("loved by both" 💞)
         − 1.0 if e conflicts with a dislike/constraint fact
rank by score → top N candidates → planner model writes the section from these candidates only

Private facts are used as signals but never shown in "Why this?" to the partner.

Caching and limits

  • Firestore collection qloo_cache, key = sha256(sorted params). TTL 24 h for insights, 7 days for search and entities.
  • httpx timeout 6 s, 2 retries with exponential backoff on 429/5xx, and a per-instance concurrency semaphore (8).
  • No fallback to fake data. On failure the tool returns {error:"taste_service_unavailable"} and the agent tells the user.

14. Couple Taste DNA Engine

  • Shared loves: entities or tags both partners like directly, plus the top results of the joint insights call that appear in both individual lists.
  • Unique flavours: high-confidence facts that only one partner has.
  • Differences: categories where both partners have strong preferences that don't overlap (e.g. a beach destination vs mountain destinations). For each difference, call insights with both signals to find a middle-ground entity.
  • Overlap score per category: Jaccard similarity on entities/tags, blended with the cosine similarity of the two partners' QLOO taste results (0–100).
  • Couple Vibe: the planner model writes a 3–5 word vibe + palette from the shared loves and tags. It's cached until the DNA changes.
  • Stored at couples/{cid}.dna, with a version number that plan sections record so they know when they're stale.

15. Plan Engine

  1. Load the space, DNA, facts, decisions and episodes.
  2. For each section in the space type's template: build the QLOO queries (type, tags, location) → candidates via couple blending.
  3. The planner model (structured output) gets the section brief + candidates + constraints and returns PlanSection, choosing from the candidates and writing reasons.
  4. Validate: every item.qloo_entity_id must be in the candidate set, otherwise the item is dropped.
  5. Budget split: a default ratio table per type → adjusted by priorities (± up to 15 % per section) → estimates labelled.
  6. Generate the timeline and to-dos from date offsets in the template (e.g. venue −120 days).
  7. Write spaces/{id}/plans/{version}. The latest pointer updates, and the client sees it in real time.
PlanSection = {
  key: "sangeet.music", title: "Sangeet Playlist",
  summary: "…",
  items: [{ id, title, qloo_entity_id?, qloo_type?, image?, est_cost?, why:[…],
            status: "suggested|liked|skipped|done" }],

16. Ever After Companion

  • partner_insight: answers using only the partner's visibility=shared facts plus the DNA. Private facts are filtered out at the query level, not by the prompt.
  • Surprise Mode: creates surprises/{id} with owner_uid only. Security rules deny the partner. The agent context for the partner never includes surprise docs.
  • Reminders: stored in reminders. A Cloud Scheduler job every 15 min sends due items through FCM, with a pre-generated idea attached.
  • Spark nudges: a weekly job; at most 1 per week per user, opt-in, based on high-confidence partner facts plus QLOO "similar" results.
  • Love status: couples.status (dating, engaged, married, parents…) changes the tone and the suggested spaces.

21. Auth, Couple Linking and Privacy

  • Firebase Auth (Google sign-in + passwordless email link).
  • Couple linking: the creator gets a couple_id → invite code (random 10 chars, expires in 7 days, single use) → the partner joins → members = 2 (hard limit).
  • Backend authorisation helpers: require_member(couple_id), require_space_access(space_id), require_owner(surprise_id).
  • Privacy filter in one function, visible_facts(viewer_uid, owner_uid), used by every tool and API. It returns everything for self, and only visibility=shared for the partner.
  • "Forget" removes facts and episodes and triggers a DNA recompute.
  • Account deletion: a cascade job removes user docs, facts and turns, and leaves the couple.

Firestore security rules (client reads)

match /spaces/{sid} {
  allow read: if request.auth.uid in get(/databases/$(db)/documents/couples/$(resource.data.couple_id)).data.members;
  allow write: if false;            // all writes go through the API
}
match /surprises/{id} { allow read: if request.auth.uid == resource.data.owner_uid; allow write: if false; }
match /users/{uid}/facts/{f} { allow read: if request.auth.uid == uid; allow write: if false; }

22. Security

  • Secrets in Secret Manager, mounted as env vars on Cloud Run. Nothing in the repo or the client bundle.
  • Cloud Run service account with least privilege: aiplatform.user, datastore.user, cloudtasks.enqueuer, secretmanager.secretAccessor, storage.objectAdmin (bucket-scoped).
  • CORS restricted to the app domains. WS origin check.
  • Rate limits per user: chat 30/min, voice 1 concurrent session, QLOO search proxy 60/min.
  • Prompt-injection safety: tool permissions are enforced on the server; content fetched from QLOO is treated as data, never as instructions.
  • Input validation with Pydantic on every tool and endpoint; widget responses are validated against the widget spec that was issued.
  • Internal endpoints accept only Google-signed OIDC tokens from the tasks and scheduler service accounts.
  • PII: only names and emails are stored. Audio is not stored by default (transcripts only).

  2. Firestore (Native) in asia-south1; create the vector and composite indexes; deploy the security rules.
  3. Store QLOO_API_KEY in Secret Manager.
  4. API: gcloud run deploy weavewed-api --source ./backend --region asia-south1 --service-account weavewed-api@… --set-secrets QLOO_API_KEY=qloo-key:latest --min-instances 1 --timeout 3600 --session-affinity (long timeout and session affinity for WebSockets).
  5. Vertex region: VERTEX_LOCATION set to a region where the chosen Live model is available (often us-central1). Latency is acceptable from India; switch regions as availability grows.
  6. Cloud Tasks queue learn-queue (max 5 concurrent); Scheduler jobs reminders (*/15), checkins (daily 10:00 IST), nudges (weekly).
  7. Frontend: npm run build → firebase deploy --only hosting, with /api and /ws rewrites to Cloud Run (or call the Cloud Run URL directly).

32. Risks and Mitigations

RiskMitigation
QLOO coverage is thin for some Indian venues or citiesUse QLOO for taste direction (cuisines, styles, artists, destinations). For specific venues, show QLOO places where available, and otherwise style guidance + "search in Maps" links. Never fabricate.
Live model names or regions changeConfig-driven model IDs; startup check that lists the available models and logs any mismatch.
Voice latency from India to US regionRegional endpoint when available; filler phrases during tool calls; keep the session warm.
Hallucinated recommendationsCandidate-only plan generation + server-side validation of entity IDs.
Privacy leak between partnersOne privacy filter function + rules + eval tests for partner_insight and surprises.
Cost spikesFlash by default, caching, per-user token budgets, learning batching.
Taste collection fatigueOne question at a time, pickers instead of typing, learn passively from chat, never more than 3 taste questions in a row.
